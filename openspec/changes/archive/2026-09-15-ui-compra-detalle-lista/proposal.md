# Proposal: Shopping List Detail UI

## Intent

Implement Grupo B (stories 050, 051, 053, 054, 057): the mobile-first shopping screen for a selected list. Users must be able to add, search, mark/unmark, edit, delete, and clear purchased articles without leaving the list detail route.

## Problem Statement

ADuo already has domain logic and application hooks for lists and articles, but there is no route or UI for the supermarket workflow. The missing detail screen blocks real use: users can create lists but cannot efficiently manage their items while shopping.

## Scope

### In Scope

- New TanStack Router route `/_privado/listas/$listaId` rendering `/listas/$listaId`.
- UI under `frontend/src/modules/listas/ui/detalle/**`.
- Consumption of `useArticulos(listaId)`, `useListas`, and `coincideConBusqueda` from `domain/busqueda.ts`.
- Pending articles displayed first; purchased articles grouped at the end and kept visible.
- Add, mark, unmark, edit, delete single article.
- Clear purchased articles for the current list.
- Search input as local view state only; it must not affect TanStack Query keys or collection/repository calls.
- Mobile-first tactile ergonomics: large touch targets for add/mark and primary actions reachable on small screens.
- Strict TDD with focused component tests before implementation.

### Out of Scope

- Backend, schema, RLS, repository, collection, realtime, and query-key changes.
- List index UI and list CRUD; handled by Grupo A.
- Household profile editing; handled by Grupo C.
- Navigation shell edits (`navegacion-app.tsx`, `marco-app.tsx`).
- Manual edits to `routeTree.gen.ts`; it is generated only.
- Installing or modifying existing shadcn components unless a needed component already exists after merge.

## Capabilities

### New Capability: `list-shopping-detail`

A route-level UI lets a household member manage articles for one list with immediate optimistic feedback from existing hooks and client-side search.

## Approach

Keep the route thin and delegate all rendering/interaction to the module UI. The page uses `useListas` to resolve the selected list's display name and `useArticulos(listaId)` for item state/actions. Article grouping is derived in render from the hook-provided ordered list and preserved after applying the local search filter. Search text lives in `useState` inside the UI component and filters with `coincideConBusqueda`.

Use semantic HTML controls and the existing `Button` component to avoid cross-group shadcn conflicts. Forms submit through hook actions and clear their local fields only on successful outcomes. Editing stays local to the visible article row and persists via `editar(id, texto)`. Delete and clear-purchased use explicit controls; empty purchased state disables clear.

| Area | Impact |

## Risks

- UI accidentally duplicates ordering already owned by the hook: keep grouping presentational and stable.
- Search could be implemented as data-fetch state: test that filtering does not call actions/fetch and do not touch query keys.
- Mobile ergonomics may regress in purely desktop-oriented markup: assert 44px minimum touch targets for add/mark/icon controls.
- Parallel Grupo A/B merge can temporarily produce a 404 from A's link before B merges; expected and accepted.

## Rollback Plan

Remove the new route file, generated route registration, and `modules/listas/ui/detalle/**`. No data, backend, schema, or shared navigation rollback is required.

## Dependencies

- Existing application hooks from task 048: `useListas` and `useArticulos`.
- Existing domain search from task 042.
- Existing UI primitives `Button`, `Alert`, `Avatar`; do not alter them.
- Grupo A may link to this route but does not need to be present for this implementation to compile.

## Success Criteria

- `/listas/$listaId` renders the selected list name and article groups.
- Pending articles appear before purchased articles; purchased remain visible and can be cleared.
- Add, mark/unmark, edit, delete, and clear-purchased invoke the correct hook actions and respond to outcomes.
- Searching `azucar` finds `Azúcar`, preserves grouping, and remains client-side view state.
- Primary shopping interactions meet mobile touch target expectations.
- Focused tests, full frontend tests, typecheck/lint/check/build pass.
